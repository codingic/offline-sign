# 验证脚本

本目录放**进程级**验证脚本：真的把 `sign` 起起来，看它在磁盘上做了什么。

与 `cargo test` 的分工很明确——

| | 覆盖什么 | 不覆盖什么 |
|---|---|---|
| `cargo test` | 加解密原语、地址派生、`open_or_fill` 的返回值 | 真实启动流程、口令交互、文件是否真的落盘 |
| 本目录脚本 | 连续两次启动后**磁盘上的字节**发生了什么 | 密码学正确性 |

两者不重复：单测比的是内存里的种子，脚本比的是磁盘上的文件。
前者漏得掉「解开后又重新加密写一遍盘」这类缺陷（种子没变，但文件被换掉了）。

## 前置

```bash
cargo build --release          # 脚本默认找 ./target/release/sign
```

也可以显式指定二进制：`scripts/verify-keystore-reuse.sh path/to/sign`。

## 脚本

### `verify-keystore-reuse.sh`

**钉住：keystore 两个文件都在时，启动只是解开，绝不重新生成私钥。**

连续起两次服务，比对两次之间 keystore 文件的 sha256 与 mtime。

判定为什么用**文件字节**而不是「地址相同」：keystore 的 salt 与 nonce 每次加密都随机，
所以只要真走过一次「生成新种子 → 加密 → 写盘」，字节必然改变。
反过来说，字节一字未变 ⟺ 一次加密都没发生过。
而「地址相同」证明不了这一点——把旧种子重新加密一遍，地址照样相同。

### `verify-partial-refill.sh`

**钉住：目录里只有一个 keystore 文件时，已有的那个绝不动，只补齐缺失的那个。**

这是 sign 里唯一「会在已有 keystore 的前提下新建私钥」的路径，所以单独一个脚本：

1. 已有的文件必须字节未变（不能被顺便重建）；
2. 补齐的确实是全新私钥（对应链的地址会变），且启动前给了警告。

第 2 点必须钉住的原因：补出来的新钥匙与用户此前（可能已收过款的）地址毫无关系。
若走到这里是误删所致，那些地址里的资产将无人控制。

## 约定

- 每个脚本自带断言，失败以**退出码 1** 退出。只打印不断言的脚本等于没有——
  行为变了也不会红。
- 临时目录用 `mktemp -d`，并用 `trap ... EXIT` 清理，不污染 `~/.allchain-sign`。
- 端口固定但互不相同（17897 / 17896），避免两个脚本并发时撞端口。
- 口令走 `SIGN_PASSWORD` 环境变量（无 TTY 环境下的启动方式），值只在脚本内部使用。
